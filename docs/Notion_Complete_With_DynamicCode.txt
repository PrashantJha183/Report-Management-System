# 1. Executive Summary

## 1.1 Business Problem

The organization relies on multiple database-driven configuration modules that control reporting, alerting, and company-level system behavior. These configurations are critical to day-to-day business operations and include:

| Configuration Area | Purpose |
| --- | --- |
| Report Definitions | Define report queries, metadata, and execution behavior |
| Report Columns | Configure report output structure and display columns |
| Report Filters | Define filtering criteria and search parameters |
| Alert Configurations | Configure automated alert generation |
| Alert Scheduling | Manage alert execution frequency and timing |
| Alert Attachments | Configure alert-related file attachments |
| Company Configurations | Store organization-wide application settings |
| Dynamic Code | Store runtime C# code overrides executed by the ERP application |

Historically, these records were managed directly through database scripts and manual SQL operations. This approach introduced several operational and technical challenges.

### 1.1.1 Key Challenges

- High dependency on database administrators and developers for routine configuration changes
- Accidental data corruption caused by manual database modifications
- Risk of unintended record deletion without recovery mechanisms
- No centralized administration interface for business users
- Lack of validation before data modifications
- No visibility into configuration changes
- Absence of audit trails for compliance and troubleshooting
- Difficulty maintaining parent-child relationships across dependent entities
- Increased operational overhead for managing configuration data
- Inconsistent management processes across different configuration modules

As the application evolved, the need for a secure, centralized, and user-friendly administration portal became increasingly important.

## 1.2 Solution Overview

The Report Management System is a centralized administrative web application developed using ASP.NET MVC 5.2.7 on the .NET Framework 4.7. The application provides a secure, web-based interface for managing report configurations, company configurations, alert configurations, scheduling information, report metadata, and other administrative entities without requiring direct database access.

The system was designed to replace manual database-driven administration processes with a structured management platform that emphasizes security, maintainability, auditability, and operational consistency across all supported business modules.

Unlike traditional configuration management systems that rely on fixed database connectivity, the application supports runtime database selection through a dynamic connection management framework. During authentication, users select the target database connection, after which the application establishes a session-specific database context. This enables the same application instance to operate against multiple SQL Server and MySQL environments without requiring code changes or separate deployments.

Authentication is implemented using XML-based user management combined with session-based authorization. User accounts, roles, and database connection information are maintained through centralized XML configuration files, allowing administrative management without modifying application code. Following successful authentication, user identity, role information, and database connection settings are stored within the ASP.NET Session and are utilized throughout the request lifecycle.

Role-based authorization ensures that users can access only the operations permitted by their assigned role. The authorization framework combines server-side request validation with user interface restrictions to prevent unauthorized operations while providing a consistent user experience.

The application follows a layered architecture consisting of Presentation, Controller, Service, Data Access, and Database layers. Business logic is encapsulated within service classes, while the Data Access Layer provides a provider-based abstraction that supports both SQL Server and MySQL databases through a unified programming model.

Every create, update, and delete operation is executed within a controlled database transaction. Prior to data modification, the existing database record is captured as a JSON snapshot and stored within the audit repository, providing complete historical traceability for compliance, troubleshooting, and recovery purposes.

In addition to database audit logging, the application maintains XML-based query logs and error logs, enabling administrators to diagnose application behavior, monitor executed SQL statements, and investigate runtime exceptions.

The Report Management System also hosts the **Dynamic Code module** — an administration IDE (Monaco editor with IntelliSense) for authoring C# code snippets that are persisted to the shared `CustomCode` table. At runtime the ERP application intercepts matching controller/action requests and executes these snippets, allowing endpoint behavior to be overridden from Report without redeploying the ERP application.

The Report Management System provides a centralized, secure, and extensible administrative platform that combines configuration management, dynamic database connectivity, comprehensive auditing, role-based security, and runtime code extensibility within a single enterprise application.

## 1.4 Project Objectives

The primary objectives of the Report Management System are:

1. Eliminate direct database dependency for routine administrative configuration management.
2. Provide a secure web-based administration portal with centralized authentication.
3. Support role-based authorization for protecting sensitive application functionality.
4. Enable runtime database selection across SQL Server and MySQL environments.
5. Maintain complete historical visibility of configuration changes through audit logging.
6. Ensure transactional consistency during all create, update, and delete operations.
7. Record executed database modification queries and runtime exceptions for operational monitoring.
8. Standardize business logic through a layered service-oriented architecture.
9. Improve maintainability through reusable design patterns and centralized configuration management.
10. Provide a scalable foundation for future enhancements including Role-Based Access Control (RBAC), external authentication providers, API integration, and application modernization.
11. Provide a mechanism for authoring runtime ERP code overrides (Dynamic Code) that take effect without redeploying the ERP application.

The Report Management System serves as the centralized administrative platform for managing reports, report columns, report filtering, alert configurations, alert schedules, alert attachments, company configurations, authentication, authorization, auditing, multi-database administration, and runtime code extensibility across the organization.

# 2. High-Level Architecture

The Report Management System follows a layered architecture pattern that separates presentation, business logic, data access, and database operations into independent layers.

This separation ensures:

- Maintainability
- Scalability
- Testability
- Security
- Database independence
- Reusability of business components

The application is built using ASP.NET MVC 5 and follows a structured request-processing pipeline where all user interactions flow through Controllers, Services, and the Data Access Layer before reaching the database.

# 3. Architectural Layers and Core System Modules

The Report Management System follows a layered, service-oriented architecture in which responsibilities are clearly separated across the Presentation, Controller, Service, Data Access, Configuration, and Database layers. Each business module is implemented using a consistent ASP.NET MVC design pattern consisting of dedicated Controllers, Services, Razor Views, JavaScript files, and CSS components while sharing common infrastructure such as authentication, authorization, transaction management, audit logging, query logging, error logging, and dynamic database connectivity.

The architecture promotes maintainability, extensibility, and database independence by isolating user interface concerns from business logic and data access. Cross-cutting services such as XML-based authentication, role management, configuration loading, operational logging, and provider-based database access are shared across all administrative modules through reusable framework components.

Each user request follows a standardized execution pipeline beginning with authentication and authorization, followed by business validation, transactional processing, auditing, and database persistence before returning the response to the client.

**Table: CustomCode**

| Column | Type | Description |
|--------|------|-------------|
| CustomCodeId | int (PK) | Auto-increment identity; shown as "Code ID" in the grid |
| ControllerName | nvarchar | Controller to intercept (e.g., VehicleCallBack) |
| ActionName | nvarchar | Action to intercept (e.g., GetVehicleModelOnManufacturer) |

Controllers:

- DynamicCodeController

  - SaveChanges (POST) — inline grid save with temp-ID mapping
  - SaveCode (POST) — compiles via RSuite DynamicCodeExecutor, then SaveCodeFromIDEAsync
  - GetCode (GET) — returns a row as JSON for the inline IDE panel
  - Delete (POST) — delete with audit capture
  - LoadClassesFromNamespaces (POST) — type names for Monaco autocomplete
- NameSpaceController — Suggest (GET) namespace/class suggestions; NamespaceEditor partial
- IntellisenseController — Completions (POST) dot-completion; Signatures (POST) method signature help; CodeEditor partial

- DynamicCodeService — GetAllAsync (in-memory sort/pagination), SaveChangesAsync, DeleteAsync, SaveCodeFromIDEAsync, GetByControllerActionAsync
- CustomCodeDAL — CRUD for the CustomCode table

Views:

- Views/DynamicCode/Index.cshtml — grid + inline IDE panel (#ideSection) + audit/Deleted Records handlers
- Views/DynamicCode/IDE.cshtml — standalone IDE fallback page
- Views/Shared/_CodeEditor.cshtml — Monaco editor partial with 3 IntelliSense providers
- Views/Shared/_NamespaceEditor.cshtml — namespace entry with suggestion list

Client-side: js/DynamicCode.js (showIDE, hideIDE, clearIDE, loadClassesForNamespaces, grid handlers). Styling: Styles/DynamicCode.css (grid + IDE panel).

Namespace handling on save (DynamicCodeController.SaveCode):

- System.Collections.Generic is excluded from the persisted Namespaces value (the compiler header already includes it)
- Report.* namespaces are excluded (Report's own assemblies cannot be resolved by the ERP runtime process)
- gacList: System.Web.dll, Microsoft.CSharp.dll

#### 4.9.3 Runtime Execution Model

```
HTTP Request to ERP controller/action
  → Global.asax.cs Application_BeginRequest
    → CallBackService.IsDynamicActionPresent(url)
        → GetByControllerAction(controller, action)   # controller + action only, no HTTP verb
        → on match: rewrite URL to DynamicCallBack/Execute
    → CallBackService.Execute
        → read Namespaces + CustomCode from CustomCode table
        → CompilerService.Compile(code, namespaces)   # recompiled EVERY request, no cache
        → Activator.CreateInstance → MethodInfo.Invoke
        → result written to HTTP response
```

Because every request is recompiled, a snippet saved in Report is active on the very next ERP request.

Code body requirement — the generated wrapper class is NOT a Controller, so the Json() helper does not exist:

```
✗ WRONG — "The name 'Json' does not exist in the current context"
return Json(new { data = "value" });

✓ CORRECT — explicit JsonResult construction
return new JsonResult
{
    Data = new { ProductModelCollection = new[] { new { Id = 1, label = "DYNAMIC MODEL" } } },
    JsonRequestBehavior = JsonRequestBehavior.AllowGet
};
```

Verified override: VehicleCallBack / GetVehicleModelOnManufacturer returns ProductModelCollection with a single DYNAMIC MODEL option, visible in the Vehicle Model dropdown on the ERP Vehicle master page (new-record form).

#### 4.9.4 Audit Integration

- UPDATE: before-image JSON captured via Dal.GetRowAsJsonAsync(DynamicCodeTable, "CustomCodeId", id) → AuditLogService.LogChangeAsync writes to com_mst_audit_log
- DELETE: same before-image capture; the audit write is wrapped in try/catch so a completed delete is never rolled back by an audit failure
- The grid exposes an inline Deleted Records button opening AuditTrail/AuditLogs.cshtml with AuditTableName = CustomCode, RecordIdLabel = Code ID

#### 4.9.5 Known Issues

| # | Issue | Impact | Location |
|---|-------|--------|----------|
| 1 | SaveCode persists broken code | Compile-failed snippet is still saved and activated in the ERP | DynamicCodeController.cs (compile result never checked before save) |
| 2 | CustomCodeDAL hardcodes SqlClient | Dynamic Code fails on MySQL (GEETEE) | CustomCodeDAL.cs (bypasses DbProviderFactory) |
| 3 | Matching without HTTP verb | GET and POST to the same controller/action cannot be overridden independently | CallBackService (ERP) |

# 5. Transaction Management

## 5.1 Overview

The Report Management System implements transaction-based processing to ensure that all create, update, and delete operations execute reliably while preserving database consistency across supported database providers.

Every database modification request passes through a standardized processing pipeline consisting of authentication, authorization, business validation, transaction management, audit logging, query logging, and exception handling before the transaction is committed.

The transaction framework guarantees that each operation either completes successfully or is rolled back entirely, preventing partial updates and maintaining referential integrity across all managed business entities.

Transaction management is implemented within the Data Access Layer through reusable transaction methods that support both SQL Server and MySQL database providers using a common programming model.

## 5.2 Transaction Processing Flow

      ▼

      ▼

      ▼

      ▼

      │
      ▼
Capture Audit Snapshot
      │
      ▼
Write Query Log
      │
      ▼
Operation Successful?
      │
 ┌────┴─────┐
 │          │
 ▼          ▼
Commit   Rollback
 │          │

# 6. Cross Database Support

## 6.1 Overview

The Report Management System supports runtime connectivity to multiple SQL Server and MySQL databases through a provider-based database abstraction architecture.

Instead of relying on statically configured database connections, users select the target database during authentication. The selected connection information is stored within the user session and is subsequently used by the Data Access Layer for all database operations.

This design enables a single application deployment to manage multiple database environments without requiring separate builds, configuration changes, or application restarts.

Database selection occurs during authentication and remains active throughout the authenticated user session.

## 6.2 Database Provider Architecture

The Data Access Layer implements a provider-independent architecture through the `IDal` interface and `Dal` implementation.

At runtime, the database provider is selected according to the authenticated user's session.

Supported providers include:

- Microsoft SQL Server
- MySQL

Provider-specific functionality such as connection objects, pagination syntax, identity retrieval, parameter creation, and SQL generation is handled internally by the Data Access Layer while exposing a unified interface to business services.

## 6.3 Configuration-Based Database Selection

Database environments are maintained through the `App_Data/DbConnection.xml` configuration file.

Each connection entry defines:

- Connection Name
- Connection String
- Database Provider Type

During user authentication:

1. User selects a database connection.
2. The selected connection is validated.
3. Connection information is stored in the ASP.NET Session.
4. The Data Access Layer retrieves the session values for every request.
5. Appropriate provider-specific database objects are created dynamically.

This architecture enables runtime database switching without recompilation or application redeployment.

## 6.4 Session-Based Database Resolution

The application resolves database connectivity dynamically using values stored within the authenticated user's session.

### Session Variables Used

| Session Variable | Purpose |
| --- | --- |
| ConnectionString | Active database connection string |
| DbType | Database provider (MYSQL / SQLSERVER) |
| CompanyCode | Friendly database name shown within the user interface |

For every incoming request, the Data Access Layer retrieves these values before creating database connections.

This design allows multiple users to connect to different database environments simultaneously without affecting one another.

## 6.5 Cross-Database Benefits

| Benefit | Description |
| --- | --- |
| Database Independence | Application logic remains unchanged |
| Flexible Deployment | Supports different client environments |
| Reduced Maintenance | Single codebase supports multiple databases |
| Simplified Migration | Easier transition between database platforms |
| Scalability | Supports future database expansion |
| Cost Optimization | Organizations can choose preferred database engines |

## 6.6 Database Provider Features

The provider-based architecture encapsulates all provider-specific behavior inside the Data Access Layer.

Capabilities include:

- Provider Factory selection
- Dynamic connection creation
- Provider-specific SQL syntax generation
- Pagination handling
- Identity retrieval
- Parameter creation
- Transaction management

The business layer remains completely independent of the underlying database provider.

## 6.7 Dynamic Code Cross-Database Limitation

The main data access path (IDal/Dal) is provider-agnostic through DbProviderFactory, but CustomCodeDAL is the exception:

- CustomCodeDAL instantiates System.Data.SqlClient types directly and does not consult the session-selected DbType
- Consequence: Dynamic Code works on SQL Server environments but fails on MySQL (GEETEE) with a provider/type error as soon as the Dynamic Code screen queries the CustomCode table
- Intended fix: mirror the GetFactory() provider switch (MYSQL → MySqlClientFactory.Instance, SQLSERVER → SqlClientFactory.Instance) inside CustomCodeDAL, resolving the provider from the session DbType

# 11. Authentication & Authorization

## 11.1 Overview

The Report Management System implements a centralized authentication and authorization framework to protect administrative functionality and ensure that only authenticated users can access application resources.

The security framework combines XML-based user management, role-based authorization, session management, and runtime database selection to provide secure access across multiple database environments.

Authentication validates user credentials, while authorization determines the operations each authenticated user is permitted to perform throughout the application.

---

## 11.2 Authentication Architecture

Authentication is implemented using XML-based user storage and session-based identity management.

### Authentication Components

| Component | Responsibility |
| --- | --- |
| Users.xml | Stores application users |
| UserService | Validates user credentials |
| HomeController | Processes login and logout requests |
| ASP.NET Session | Stores authenticated user context |
| LoginAuthorizeAttribute | Protects secured resources |

## 11.3 XML-Based User Management

Application users are maintained within the **Users.xml** configuration file.

Each user record contains:

- UserId
- Username
- Password
- DisplayName
- Role

The UserService validates user credentials by comparing the supplied username and password against the XML configuration.

Passwords are intentionally stored in plain text based on current project requirements. Future releases should migrate to hashed password storage using a secure password hashing algorithm.

## 11.4 Plain-Text Password Storage

Passwords are deliberately stored and compared as plain text. The previous implementation used PBKDF2 password hashing with random cryptographic salts (via the .NET `Rfc2898DeriveBytes` class), but that encryption and salting was removed from the application (commit 61056dc) — no hashing, salt generation, or encryption is applied today.

During authentication, `UserService.ValidateUserAsync` simply compares the supplied password directly against the plain-text `<Password>` value stored in `Users.xml`. The same direct comparison is used for password changes and administrative password resets.

This plain-text approach is a known security limitation (see 14.1). Future releases should migrate to a secure password hashing scheme — for example by adopting ASP.NET Identity with built-in PBKDF2/BCrypt hashing — without changing the login workflow.

## 11.5 Login Process

The login process performs the following sequence:

1. User enters Username and Password.
2. User selects the target database connection.
3. HomeController receives the login request.
4. UserService validates credentials.
5. Selected database configuration is loaded.
6. Authentication session is created.
7. User is redirected to the application dashboard.

Authentication failure returns the login page with validation messages while preserving the previously entered username and selected database connection.

## 11.6 Password Change Management

The application provides two independent password management workflows.

### 11.6.1 Self-Service Password Change Architecture

The Report Management System allows authenticated users to change their own passwords through the `AccountController`. The password change process verifies the user's existing credentials before storing the new plain-text password.

Password updates are processed entirely within the `UserService`, ensuring that validation, XML persistence, and audit logging remain centralized within the business layer.

Before a password change is accepted, the business layer validates several security requirements to ensure password integrity and prevent accidental credential changes.

Validation includes:

- New password must satisfy the minimum password length.
- New password and confirmation password must match.
- New password must differ from the current password.

# 13. Security, Deployment & Operational Considerations

The Report Management System protects administrative functionality through XML-based authentication, role-based authorization, session management, validation, transactional processing, audit logging, and operational logging.

## 13.2 Password Storage

The Report Management System previously protected user credentials using PBKDF2 password hashing with unique cryptographic salts. That encryption and salt-based hashing was removed (commit 61056dc); the application currently stores and compares passwords as plain text.

Passwords are stored in reversible, unencrypted form in `Users.xml`. This is a known security limitation (see 14.1) — no hashing, salt generation, constant-time comparison, or Base64 encoding is applied today.

# 14. Known Limitations & Technical Debt

Although the Report Management System satisfies the current business requirements, several enhancements remain for future releases.

## 14.1 Current Architectural Limitations

| # | Limitation | Business Impact | Technical Details | Recommended Improvement |
| --- | --- | --- | --- | --- |
| 1 | XML-Based User Storage | Manual user management | Users maintained in Users.xml | Migrate to ASP.NET Identity or Active Directory |
| 2 | No Password History Enforcement | Password reuse possible | Previous passwords are not retained | Prevent reuse of recently used passwords  |
| 3 | No Password Expiration Policy | Long-lived credentials | Psswords do not expire automatically | Implement configurable password expiration policies  |
| 4 | No RBAC Granularity | Limited permissions | Only SuperAdmin and Database Administrator roles | Add configurable role management |
| 5 | Manual AlertConfigId Generation | Concurrency risk | Uses MAX(Id)+1 | Replace with identity column |
| 6 | Hard Delete Strategy | Recovery limitation | Physical deletion | Implement soft delete |
| 7 | Bootstrap 3 | Legacy UI | Older framework | Upgrade to Bootstrap 5 |
| 8 | No Automated Unit Testing | Regression risk | Manual testing | Add unit & integration tests |
| 9 | Fixed IST Timezone | Regional limitation | Hardcoded timezone | Configurable timezone support |
| 10 | Client-Side Link Lookup | Performance limitation | Loads all records | Server-side autocomplete |
| 11 | Legacy Sync Code | Maintainability | OLD_SYNC regions retained | Remove deprecated code |
| 12 | No Anti-Forgery Tokens | Security risk | POST actions not protected | Apply ValidateAntiForgeryToken |
| 13 | Synchronous Controllers | Scalability | ActionResult used | Convert to async controllers |
| 14 | XML Log Growth | Storage usage | Daily XML logs continue growing | Implement log archival |
| 15 | Session-Based Authentication | Single-server dependency | ASP.NET Session | Consider JWT/OpenID Connect |
| 16 | SaveCode Persists Broken Code | Broken overrides activate in the ERP | DynamicCodeController.SaveCode ignores the compile result before saving | Check compiler result and block the save on compile failure |
| 17 | CustomCodeDAL Is SQL Server-Only | Dynamic Code fails on MySQL/GEETEE | DAL bypasses DbProviderFactory and hardcodes SqlClient | Make CustomCodeDAL provider-agnostic (mirror Dal.GetFactory()) |
| 18 | ERP Matches Without HTTP Verb | GET and POST overrides can collide | Matching uses controller + action only | Add an HttpMethod column to the CustomCode table |
| 19 | Monaco Editor Loaded From CDN | External network dependency | Editor won't load without internet access | Bundle Monaco locally |
| 20 | Dynamic Code Executes Arbitrary C# | Security/operational risk | No sandbox; capability is gated only by admin authentication | Add sandboxed execution and a publish/approval workflow |
| 21 | Plain-Text Password Storage | Credential disclosure risk | Passwords stored unencrypted in Users.xml; no hashing or salt (removed in commit 61056dc) | Migrate to ASP.NET Identity with secure password hashing |

## 14.2 Future Improvement Priorities

### 14.2.1 High Priority

- ASP.NET Identity
- Password Hashing
- Multi-Factor Authentication
- Anti-Forgery Protection
- Enforce the compile-result check in DynamicCodeController.SaveCode so broken code is never saved
- Make CustomCodeDAL provider-agnostic so Dynamic Code works on MySQL

### 14.2.2 Medium Priority

- Server-side Search

# 15. Conclusion

The Report Management System provides a secure, centralized, and scalable administrative platform for managing reports, report metadata, alert configurations, scheduling information, company-level configurations, user administration, password management, and XML-based identity management across multiple SQL Server and MySQL environments.

The application combines a layered ASP.NET MVC architecture, XML-based plain-text authentication, role-based authorization, centralized user administration, dynamic database connectivity, transaction management, comprehensive audit logging, and XML-based operational logging into a unified enterprise administration solution.

Through provider-independent database access, centralized configuration management, reusable service-oriented components, standardized processing workflows, and secure identity management, the application delivers high maintainability, deployment flexibility, operational transparency, and enterprise-grade security.

The Dynamic Code module extends this platform further: administrators author C# runtime overrides in an inbuilt Monaco IDE, and the ERP executes them against the shared CustomCode table without any ERP redeployment, creating a single administrative portal that controls both configuration data and runtime ERP behavior.

The architecture has been designed to support future enhancements such as ASP.NET Identity, Multi-Factor Authentication (MFA), advanced role management, password history enforcement, password expiration policies, API integration, cloud deployment, and continued modernization while preserving compatibility with the current business environment.
